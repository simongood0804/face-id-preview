# 推流联调 · 手动从零启动手册

> 目标：**从冷机状态出发，纯手工**把「车机 → MediaMTX → 浏览器」整条链路跑起来，并支持从浏览器反向切换摄像头。
> 本文只写人的操作步骤与判据，不涉及改代码。端口、路径、命令均与当前工程一致（2026-10 实测）。
>
> **PC 侧启动就是一条命令：`make pc-up`（见 §2，含它内部做了什么）**，其余小节只解释"为什么"和"怎么判断对错"；
> 只想敲命令的话直接看 **§6 命令速查**（PC + 车机一屏内）。

## 0. 全景：谁连谁

```
 ┌──────────┐   WHIP 推流(HTTP POST SDP)   ┌──────────────┐   WHEP 播放   ┌──────────┐
 │  车机 App │ ──────────────────────────▶ │   MediaMTX   │ ────────────▶ │  浏览器   │
 │           │      /test/whip  :8889       │  PC: 8889    │   /test/whep  │ 播放+按钮 │
 └──────────┘                              └──────────────┘               └────┬─────┘
       ▲                                                                       │
       │        WebSocket ws://<PC>:8081/ws?role=device   {"cam": N}           │
       └───────────────────────  控制中继 server.py  ◀─────────────────────────┘
                         （浏览器用 role=ui 连它；按钮在浏览器上）
```

三段可独立验证：
1. **MediaMTX 起着** = 推流能被收下、播放页能打开；
2. **控制中继起着** = 浏览器上的切换按钮有反应（**不起也不影响推流/录制**）；
3. **车机在推流** = 浏览器能看到画面。

## 2. PC 侧：启动（一条命令 `make pc-up`）

### 2.1 一键启动（一条命令）

```bash
cd /Users/simon/Desktop/Projects/algorithm/face_id
make pc-up
```

`make pc-up` 内部做的事（**幂等**：重复执行安全，已在跑的会跳过）：

| 步骤 | 动作 | 等价手工命令 |
|---|---|---|
| ① | 缺配置才写最小 `~/mediamtx.yml`（无配置文件时 `paths` 为空，任何流名都会被拒） | `[ -f ~/mediamtx.yml ] \|\| printf 'paths:\n  test:\n    source: publisher\n' > ~/mediamtx.yml` |
| ② | 起 MediaMTX（已在跑则跳过；`cd ~` 才会读到 `~/mediamtx.yml`） | `pgrep -q mediamtx \|\| (cd ~ && nohup mediamtx > /tmp/mediamtx.log 2>&1 &)` |
| ③ | 起控制中继（已在跑则跳过；**可选**，只影响浏览器切摄像头） | `lsof -nP -i :8081 >/dev/null \|\| (cd <库仓库>/tools/camera-switch-demo && nohup python3 server.py > /tmp/relay.log 2>&1 &)` |
| ④ | 自检 + 打开播放页 | `make pc-check` / `open "http://$(ipconfig getifaddr en0):8081/"` |

其它两个目标：

```bash
make pc-check      # 只自检（播放页/配置的 HTTP 码、中继 /state）
make pc-down       # 停止 MediaMTX 与控制中继
```

路径/端口可用变量覆盖，例如：
```bash
make pc-up RELAY_DIR=/path/to/camera-switch-demo WHIP_PORT=8889 RELAY_PORT=8081 \
           MEDIAMTX_CONFIG=~/my.yml PAGE_HOST=192.168.6.233
```

`PAGE_HOST`（打开播放页用的主机）的选择规则：**多网段时优先 `192.`**——演示通常跑在 192 网段的 WiFi 局域网；
这台 Mac 是 `en1=192.168.6.233`，而 `en0` 在另一个网段（`10.14.11.42`），所以**不要用 `ipconfig getifaddr en0`**。
规则具体是：本机所有非回环 IPv4 → 优先 `192.*` → 否则第一个 → 都没有则 `localhost`。
车机侧 `RelayDiscovery` 的网段推导用的是同一条规则（否则会去扫蜂窝网段 `10.202.83.x`，永远找不到中继）。

页面里的 MediaMTX 地址也可以用 URL 参数临时改，不必动代码：
`http://192.168.6.233:8081/?media=192.168.6.233:8889&stream=test`。

### 2.2 自检（通过后再去车机点「开始推流」）

```bash
make pc-check
#   播放页/配置 : 200                     ← 期望 200
#   中继 /state : {"cam": 1, "seq": 0}    ← 起了中继才有；没起会显示"不可达"
tail -5 /tmp/mediamtx.log                # 顺带看有没有 ERR
```

| 结果 | 含义 |
|---|---|
| `播放页/配置: 200` | ✅ path 已放行，可以推流 |
| `500 {"error":"path 'test' is not configured"}` | ❌ 配置没生效（`paths` 为空）→ 见 §2.4 |
| `curl: (7) Failed to connect` | ❌ 没起或没监听 8889 → 见 §2.3 看是不是双实例冲突 |

### 2.3 全部停掉

```bash
make pc-down      # 停掉中继与 MediaMTX，并回显两者是否已停
```
> MediaMTX **同一时刻只能有一个实例**：重复启动会 `listen udp :8000: bind: address already in use` 后自动退出（无害，但会让人以为"起来了"）。

### 2.4 细节（出问题或有特殊需求时看）

**a) 配置文件决定「哪些流名被允许」**——取决于启动方式，别搞混：

| 启动方式 | 读哪个配置 | 内容要点 |
|---|---|---|
| 手工前台（`cd ~ && mediamtx`，即 §2.1 的做法） | `~/mediamtx.yml` | 最小配置：只放行 `test`（`source: publisher`） |
| brew 服务（`brew services start mediamtx`） | `/opt/homebrew/etc/mediamtx/mediamtx.yml` | formula 自带模板，`paths: all_others:` → **任意流名都放行** |

想改成开机自启：先 `pkill mediamtx`（否则端口冲突），再 `brew services start mediamtx`；
日志随之改到 `/opt/homebrew/var/log/mediamtx/`。

**b) 推流入口是否放行的验证法**（比看播放页更直接）：
```bash
curl -s -i -m 5 -X POST http://127.0.0.1:8889/test/whip \
     -H "Content-Type: application/sdp" --data "v=0" | head -8
# 空 SDP 被解析到 → 返回 {"error":"EOF"} 才算"已放行"
# 若仍返回 path 'test' is not configured → 配置没生效
```

**c) 中继的行为与参数**（`python3 server.py`）：
- 监听 `0.0.0.0:8081`；环境变量 `CSWITCH_PORT` / `CSWITCH_STREAM`（默认 `test`）/ `CSWITCH_CAMS`（默认 6）；
- ⚠️ **初始状态就是 `{"cam": 1}`**，车机首次轮询成功后会**自动切到第 1 路**（App 日志出现 `中继：switch -> 1`）——设计如此，不是异常；
- 不启动它时，车机日志每约 1.3 s 打一条 `relay unreachable`（§5 排障表第 3 条）。

**d) 播放页**（由中继托管，**不能双击 `index.html`**：页面里 `/state`、`/switch` 是相对路径、
WebSocket 用 `ws://${location.host}`，`file://` 下全废）：

```bash
open "http://192.168.6.233:8081/"     # 参数都有默认值，通常不用写
# 显式版：open "http://192.168.6.233:8081/?media=192.168.6.233:8889&stream=test"
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `media` | `${当前主机名}:8889` | MediaMTX 的 host:port |
| `stream` | `test` | 流名（须与 App 推流地址一致） |
| `cams` | `index.html` 里 `DEFAULT_NAMES` 长度 | 按钮数，**必须与中继 `CSWITCH_CAMS` 一致** |
| `names` | `DEFAULT_NAMES` | 临时覆盖按钮显示名（逗号分隔） |

**按钮 ↔ 车机摄像头编号的约定**（两边必须一致，当前一致）：

| 序号 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| `index.html` `DEFAULT_NAMES` | AVMF | AVMR | AVMB | AVML | RVC | DMS |
| 车机 `SWITCH_CAMERA_ORDER` | AVMF | AVMR | AVMB | AVML | RVC | DMS |

## 3. 车机侧：部署 + 开推流

### 3.1 部署（**唯一正确方式**）
```bash
cd /Users/simon/Desktop/Projects/algorithm/face_id
make push-system
```
依次：clean-build → `adb root`/remount → push APK 到 `/system/app/DmsFace/` → push native 库 →
push 模型到 `/vendor/etc/faceid/` → 清应用模型缓存 → chmod/chown → 清 oat → **重启设备**。

> **禁止** `make install` / `adb install`：装成数据应用后拿不到 `libevsservicejni.so` 等
> EvsSDK 系统库，取流不可用。

重启完成后**务必查一眼 ABI**（历史踩过的坑，见 §5 排障表）：
```bash
adb shell "dumpsys package com.skyworth.faceid" | grep primaryCpuAbi   # 期望 arm64-v8a
```

### 3.2 启动与操作
```bash
make run        # 或车机上手动点开 App
```
路径：**主页 → 推流测试校验 →〔可选〕对端地址（填 PC 的 IP）→ 开始推流**。

- 推流地址 = `http://<对端>:8889/test/whip`，流名 `test`，断线最多 30 s 重连一次；
- 对端地址是运行期持久化配置（PC 走 WiFi 时 IP 会变），也可用页面里的自动发现；
- 顶部状态行与按钮是**可恢复的一对**：

| 状态行 | 按钮 | 含义 |
|---|---|---|
| 灰 `未推流` | `开始推流（surface）` | 空闲 |
| 绿 `● 推流中 · 29.8fps · 投 3400 帧 · 编码 3399 帧` | `停止推流` / `停止录制` | 正在推流（实时摘要每约 2 s 刷新） |
| 橙 `正在停止（保存输出文件）…` | 置灰 `正在停止…` | 收尾中，此时禁止开新会话 |

- **离开本页会收尾当前会话**（finalize 输出文件）；
- 一次只允许一个 native 会话：收尾期间再点「开始」会被拒绝，需**再点一次**。

## 5. 故障排查表

| 现象 | 原因 | 处理 |
|---|---|---|
| 播放页 `path 'test' is not configured`（500） | MediaMTX 的 `paths` 为空（无配置文件） | §2.4 a) 放一份配置并重启 |
| 播放页 `no stream is available on path 'test'`，但 MMTX 日志里有车机 session | **车机没吐出媒体**（编码器无输出） | 看 §4-2 的 `emitted`；历史上是 EGL 上下文跨线程导致 `EGL_BAD_ACCESS`（见附录） |
| 车机日志刷 `relay unreachable: Failed to connect to <PC>:8081` | 控制中继没启动 | 无害；要切换功能就 §2.1 ③ |
| `listen udp :8000: bind: address already in use` | 起了**两个** MediaMTX | 只留一个：`pgrep -l mediamtx` → `kill <pid>` 后重起 |
| 播放页按钮点了没反应 | 按钮数与中继 `CSWITCH_CAMS` 不一致（中继直接 400/丢弃） | 两边改成同一路数并重启中继 |
| MMTX 有 publisher，浏览器仍无画面 | `8189/UDP` 被防火墙拦（最易忽略） | 放行 §1 的 UDP 端口 |
| App 启动即崩 / `UnsatisfiedLinkError` | `primaryCpuAbi` 被刷成 `armeabi-v7a`，native 库加载不到 | `dumpsys package … \| grep primaryCpuAbi`；清 `/data/system/packages.xml` 中该包的 `primaryCpuAbi` 属性后重启（成因未完全查明，每次 push 后都查一眼） |
| 画面上下颠倒 / 被拉伸 / 只有下 1/3、其余发绿 | 历史问题：EGL 采样整块 gralloc（1600×3900 只有顶部 1600×1300 是画面）+ Y 翻转配置 | 已在 `encoder_surface_renderer.cpp` 修复（子矩形采样 + `kFlipY`）；换平台若又颠倒就改 `kFlipY` |
| 推流按钮卡在「正在停止…」无法再点 | 历史问题：收尾线程异常未兜底 | 已修（`try/catch/finally` 保证界面复位） |

## 附录：两个容易反复踩的根因（备查）

1. **库的渲染 API 有线程绑定**
   `mr_render_create / mr_render_frame / mr_render_destroy` 必须在**同一个线程**调用：
   库的 `RenderContext::CreateFromNativeWindow()` 内部会 `eglMakeCurrent` 且**不释放**，
   context 就留在创建它的线程上；跨线程时每帧 `eglMakeCurrent` 报 `EGL_BAD_ACCESS`，
   画面一帧都进不了编码器输入 surface，最终表现为 `encoder_polls > 0 而 encoder_emitted == 0`。
   车机侧现已固定用同一个渲染线程承接这三个调用。

2. **关键帧间隔 `gop_size` 的单位是「秒」**
   `VideoEncoderNode` 的 `gop_size` 在 Android 后端直接对应 `i-frame-interval`（秒），
   FFmpeg 后端才乘 `fps`。工程内统一用 `gop_size: 1` = **每秒一个 I 帧**；
   写 30 会变成 30 秒一个关键帧（播放端起播慢、丢包恢复慢）。
