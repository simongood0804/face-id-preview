## 1. 项目概述

基于 **Android 10**（`minSdk 29` / `targetSdk 29` / `compileSdk 31`），系统应用（`android.uid.system` 共享 UID），利用 **EvsSDK**（`com.android.car:evs:1.0.7`）控制 DMS 摄像头，实现驾驶员监控（DMS）人脸识别与预览。

### 核心流程

> **v3.0 修订**：取消 ROI 裁剪，算法直接使用**全图**推理；入口由单 `PreviewActivity` 改为 `HomeActivity` + 三大模块。

```
HomeActivity（三入口）
 ├─ 人脸识别 RecognitionActivity（DETECTION|RECOGNITION|LIVENESS|LANDMARK）
 ├─ 疲劳监测 FatigueActivity    （DETECTION|LANDMARK）
 └─ 分心监测 DistractionActivity（DETECTION|HEADPOSE|GAZE|LANDMARK）

EVS 摄像头取流 → 帧数据读取（全图 1600×1300） → 算法推理（检测/识别/姿态/视线/分心） → 分心判定防抖 → Overlay 按模块分区绘制 → 预览显示
```

### 核心约定

- **算法类型**：自研算法，通过 AAR 集成（`face-sdk-v1.1.4.aar`），算法团队实现 `IFaceIDAlgorithm` 接口
- **算法输入**：RGB888 **全图帧数据（1600×1300，取消裁剪）** + 宽高（v3.0 起，见 §5.3）
- **算法输出**：`FaceIDResult`（人脸框、关键点、地标、头姿、视线、分心、DMS 分区等）——**坐标天然为原图空间，无需点位映射转换**
- **关键要求**：分层解耦、故障隔离——某一层故障不影响其他层；避免因未及时归还 Buffer 导致阻塞
- **会话复用**（v3.0）：算法/帧会话均为**进程级单例 + 引用计数**，模块切换复用同一资源（见 §16.4）

## 2. 分层架构设计（v2.0）

项目采用**五层架构**，借鉴 openpilot 的"共享内存 + 服务注册 + 轮询分发"消息总线思想。

```
┌─────────────────────────────────────────────────────────────────────────┐
│                         UI 层  ui/PreviewActivity                        │
│   装配各层模块 + UI 交互（按钮/文本/dump 控制），仅负责展示               │
├─────────────────────────────────────────────────────────────────────────┤
│              图像绘制层  render/FaceOverlayView                          │
│   Canvas 叠加绘制：人脸框/关键点/地标/头姿/视线/zone 面板/分心提示        │
├─────────────────────────────────────────────────────────────────────────┤
│              信号转发层  signal/                                         │
│   VehicleSignalSource（车机信号）+ DistractionStateMachine（分心防抖）   │
│   + SignalDispatcher（轮询分发 + 故障上报）                              │
├─────────────────────────────────────────────────────────────────────────┤
│            图像帧数据管理层  frame/ + camera/ + algorithm/               │
│   FrameSource（帧源抽象）+ FrameDistributor（帧分发）+ FrameProcessor    │
│   + IFaceIDAlgorithm（算法接口）+ FaceIDAlgorithmImpl（AAR 实现）        │
├─────────────────────────────────────────────────────────────────────────┤
│                  消息总线  bus/（进程内发布/订阅）                        │
│   ServiceRegistry/BusQueue/BusHub/BusPublisher/BusSubscriber/HealthMonitor│
└─────────────────────────────────────────────────────────────────────────┘
```

### 2.1 分层原则

1. **单向依赖**：UI → 绘制层 → 信号层 → 帧层，只允许上层依赖下层抽象。
2. **仅通过总线通信**：层与层之间不直接调用对方具体类，通过命名 Topic 发布/订阅。
3. **故障隔离**：per-topic 健康检查 + reader 独立指针 + 错误事件分级 + 回调异常隔离，实现"单层故障只上报不崩溃"。
4. **消息只传递值对象**：载荷均为不可变值对象，避免跨层共享可变状态。

### 2.2 目录结构

```

├── signal/    信号转发层（阶段二）
```

## 3. 消息总线（bus）— 阶段一

参照 openpilot 的 `msgq`（共享内存环形缓冲）+ `services.py`（服务注册）+ `PubMaster/SubMaster`（发布/订阅）。

### 3.1 Topic 注册表（ServiceRegistry）

```kotlin
enum class Topic(val freqHz: Int, val isCritical: Boolean = true) {
    VEHICLE_SPEED(10),   // 车机车速
    ALGO_RESULT(20),     // 算法结果
    ALGO_STATE(1),       // 算法健康状态
    FRAME_READY(30),     // 帧已就绪
    FRAME_OVERLAY(20),   // 绘制层可消费的 overlay 数据
    SIGNAL_ERROR(1),     // 信号层故障上报
    FRAME_ERROR(1),      // 帧层故障上报
    BUS_HEARTBEAT(1)     // 总线心跳（watchdog 基准）
}
```

**健康超时**：`healthTimeoutMs(topic) = (3 * 1000) / freqHz` ms（`HEALTH_CHECK_MULTIPLIER = 3`）。频率越低，允许失活窗口越长。

### 3.2 单写多读环形队列（BusQueue）

- 一个队列对应一个 Topic，通常**一个发布者 + 最多 15 个订阅者**（`DEFAULT_MAX_READERS = 15`）。
- **读写指针分离**：`writeSeq`（写指针）+ `readerPositions`（每个 reader 独立读指针），互不干扰。
- **慢读者隔离**：发布者写数据时不等待最慢读者，慢读者通过独立指针追赶，不阻塞发布者。
- **原子操作**：`registerReader()` 用 CAS 递增 `readerCount` 抢占槽位。

```kotlin
class BusQueue(capacity: Int = 64, maxReaders: Int = 15) {
    fun registerReader(): Int        // 注册订阅者，返回 reader id
    fun unregisterReader(readerId: Int)
    fun publish(msg: BusMessage): Long  // 单写者发布
    fun readNext(readerId: Int): BusMessage?  // 独立读指针读取
    fun hasNext(readerId: Int): Boolean
}
```

### 3.3 总线枢纽与发布/订阅

- **BusHub**：`ConcurrentHashMap<Topic, BusQueue>`，管理各 topic 队列与 reader 注册/发布/读取。
- **BusPublisher**（对应 PubMaster）：`publish(topic, payload): Long`，按 topic 维护自增序号。
- **BusSubscriber**（对应 SubMaster）：`update()` 轮询所有订阅 topic，拉取新消息保留最新一条，做 per-topic 健康检查。

```kotlin
class BusSubscriber(bus: BusHub, topics: Set<Topic>) {
    fun update(nowNanos: Long = System.nanoTime())  // 轮询 + 健康检查
    fun alive(topic: Topic): Boolean                // 该 topic 是否存活
    fun updated(topic: Topic): Boolean              // 上一轮是否有新消息
    fun latest(topic: Topic): BusMessage?           // 最新消息
    fun <T> latestPayload(topic: Topic, clazz: Class<T>): T?  // 类型安全取载荷
}
```

### 3.4 消息容器（BusMessage）

```kotlin
data class BusMessage(
    val topic: ServiceRegistry.Topic,  // 消息所属 topic
    val payload: Any,                  // 载荷（不可变值对象）
    val sequence: Long,                // 单调递增序号
    val timestampNanos: Long           // 发布时间戳（单调时钟）
)
```

### 3.5 健康监控器（HealthMonitor，Watchdog 角色）

监控一组关键 topic 的 alive 状态，检测"健康→失活"状态转变并上报故障。

```kotlin
class HealthMonitor(monitored: Map<Topic, String>, bus: BusHub, onFault: ...) {
    fun update(nowNanos: Long = System.nanoTime())  // 周期性健康检查
    fun healthy(topic: Topic): Boolean              // 是否健康
    fun isFaulted(topic: Topic): Boolean            // 是否失活
    fun lastFault(topic: Topic): FaultEvent?        // 最近故障
}
```

**容错要点**：单个 topic 失活只影响自身；故障通过 `onFault` 回调上报（不抛异常）；回调异常被隔离不外传。

## 4. 信号转发层（signal）— 阶段二

### 4.1 值对象（SignalTypes）

```kotlin
data class VehicleSpeed(val speedKmh: Float, val valid: Boolean)       // 车速
data class AlgoDistractionInput(val hasFace: Boolean, val gazeDistracted: Float)  // 分心输入摘要
data class DistractionOutput(val distracted: Boolean, val activeThresholdMs: Long, val speedBand: String)  // 分心输出
data class FaultEvent(val code: String, val source: String, val message: String)  // 故障事件
```

### 4.2 分心判定状态机（DistractionStateMachine）

从 `PreviewActivity` 提取的纯逻辑，按"持续时间"累计判定（非帧数，因单槽替换+跳帧导致帧率不稳定）。

| 常量 | 值 | 说明 |
|------|-----|------|
| `TRIGGER_MS_FAST` | 1500ms | 快速档（≥50km/h 或无车速数据） |
| `TRIGGER_MS_SLOW` | 3000ms | 慢速档（<50km/h） |
| `CLEAR_MS` | 500ms | 解除阈值 |
| `SPEED_FAST_THRESHOLD_KMH` | 50f | 分档车速阈值 |

```kotlin
class DistractionStateMachine(clockMs: () -> Long = { SystemClock.elapsedRealtime() }) {
    fun update(hasFace: Boolean, gazeDistracted: Float, vehicleSpeedKmh: Float): Boolean
    fun reset()
    fun isDistracted(): Boolean
    fun currentTriggerMs(): Long
    fun currentSpeedBand(): String  // "fast" / "slow"
}
```

**算法逻辑**：
- 未触发态：连续分心达到当前车速阈值 → 触发
- 已触发态：连续非分心达到 `CLEAR_MS` → 解除
- 无人脸 → `reset()`

**设计细节**：用显式 `timingActive` 布尔标志替代"时间戳为 0"哨兵，避免时钟从 0 开始的边界问题。

### 4.3 车机车速信号源（VehicleSignalSource）

封装 Car VHAL 的 `CarPropertyManager` 车速订阅（`PERF_VEHICLE_SPEED`，m/s → km/h × 3.6）。

```kotlin
class VehicleSignalSource(context: Context) {
    var speedKmh: Float       // -1 = 无数据
    var isValid: Boolean
    var onSpeedChanged: ((VehicleSpeed) -> Unit)?  // 车速变化回调
    fun connect() / fun disconnect()
}
```

**容错**：连接失败/断开/属性错误 → 车速置 -1（无效），不抛异常；按最严格档处理。

### 4.4 信号分发器（SignalDispatcher）

核心消费者，轮询 `VEHICLE_SPEED` + `ALGO_RESULT`，做分心判定，发布 `FRAME_OVERLAY`。

```kotlin
class SignalDispatcher(hub, publisher, distractionExtractor, stateMachine) {
    fun poll(nowNanos: Long = System.nanoTime())   // 轮询 + 健康检查 + 故障上报
    fun processAlgorithmResult(result: FaceIDResult)
    fun processVehicleSpeed(speed: VehicleSpeed)
    var lastDistraction: DistractionOutput
    var lastFault: FaultEvent?
    var vehicleSpeedHealthy: Boolean
    var algoHealthy: Boolean
}
```

**故障上报**（阶段五强化）：`poll()` 检测车速 topic 失活 → 发布 `SIGNAL_ERROR` + 记录 `lastFault`；车速故障**不影响算法分心判定**（按 fast 档降级）。

## 5. 图像帧数据管理层（frame + camera + algorithm）— 阶段三

### 5.1 帧源抽象（FrameSource）

```kotlin
interface FrameSource {
    fun start(cameraId: String)
    fun stop()
    var onFrameData: ((HardwareBuffer, Int, Int) -> Unit)?   // 新帧回调
    var onFrameSizeChanged: ((Int, Int) -> Unit)?            // 帧尺寸变化
}
```

`FaceIDCameraController` 实现 `FrameSource`（同时保留 `EvsBufferProvider` 渲染接口）。

### 5.2 帧分发器（FrameDistributor）

统一管理"帧源 → 算法帧处理"的分发路径。

```kotlin
class FrameDistributor(
    frameSource: FrameSource,
    frameProcessor: FrameProcessor,
    readFrame: (HardwareBuffer, Int, Int) -> ByteArray?,  // 帧有效期内读取数据
    algorithmEnabled: () -> Boolean                        // 算法开关
) {
    fun attach() / fun detach()
    var frameWidth / frameHeight
}
```

- 收到帧 → 在帧有效期内 `readFrame` 读为 ByteArray → `frameProcessor.submitFrame()`。
- **故障隔离**：读取/提交异常被捕获记录，不中断帧源与其他消费者。
- **保持渲染独立**：EVS 渲染路径（`getNewFrame`）不经过本分发器。

### 5.3 帧处理器（FrameProcessor）— 解耦后

> **v3.0 修订**：从依赖具体类 `FaceIDAlgorithmImpl` 改为依赖 `IFaceIDAlgorithm` 接口；并**取消 ROI 裁剪，改用全图推理**（原 900×900 裁剪方案见 FACEP-003，已回退，见 §16.5）。

```kotlin
class FrameProcessor(
    mAlgorithm: IFaceIDAlgorithm,     // 解耦：接口而非具体类
    mExecutor: ExecutorService,
    mCallback: (FaceIDResult) -> Unit
) {
    @Volatile var cropLeft / cropTop  // 保留字段（全图推理下恒为 0，兼容旧引用）
    fun submitFrame(data: ByteArray, w: Int, h: Int)
}
```

**单槽替换 + 全图推理**：
- 单槽替换（`mPending`），跳帧处理，避免堆积；
- **全图 UYVY → RGB888 一次转换（1600×1300，不裁剪）**；
- 直接 `processFrame(rgb, 1600, 1300, 0)`，**`setCropOffset(0, 0)`**——算法返回坐标天然为原图空间，**无需点位映射转换**；
- 性能：有人脸每帧约 82ms（中位数）、无人脸约 35ms，偶发尖峰 160ms+。

### 5.4 算法抽象接口（IFaceIDAlgorithm）

阶段三为解耦新增了带默认实现的接口方法：

```kotlin
interface IFaceIDAlgorithm {
    class FaceIDResult(...)   // faceId/confidence/faceRect/keypoints/landmarks/headpose/gaze/zone 等
    fun initialize(context, config): Boolean
    fun processFrame(frameData, width, height, format): FaceIDResult
    fun setCropOffset(x: Int, y: Int)   // 默认空实现，算法可重写做坐标修正
    fun dumpOriginalFrame(uyvyData, width, height)  // 默认空实现，算法可重写缓存调试帧
    fun release()
}
```

**注意**：`FaceIDResult` 构造函数对 `processedData` 做防御性拷贝，保证不可变。

## 6. 图像绘制层（render）— 阶段四

### 6.1 FaceOverlayView

从 `ui/` 迁移到 `render/`，**绘制逻辑完全保留**（543 行原样迁移，仅改包名）；**v3.0 增加 `drawMode` 分区绘制**，各模块绘制不同内容（见 §16.6）。

```kotlin
class FaceOverlayView : View {
    // v3.0：按模块分区的绘制模式（由 FaceOverlayBridge.setFaces 时设置）
    var drawMode = DRAW_MODE_DISTRACTION
    fun setFaces(faces: List<FaceBox>, imgW: Int, imgH: Int)  // 更新人脸列表并重绘
```

## 8. 完整数据流

### 8.1 帧数据流

```
EVS HAL → FaceIDCameraController (FrameSource.onFrameData)
  │
  ├─▶ [渲染路径] getNewFrame() → EvsGL20CameraRenderer → GLSurfaceView 预览
  │
  └─▶ FrameDistributor.onFrame → readHardwareBuffer (JNI UYVY→ByteArray)
        └─▶ FrameProcessor.submitFrame (单槽替换)
              ├─▶ dumpOriginalFrame (调试缓存)
              ├─▶ convertFullFrame (全图 1600×1300 UYVY→RGB888，不裁剪)
              ├─▶ mAlgorithm.setCropOffset(0, 0)  // 无偏移，坐标即原图空间
              ├─▶ IFaceIDAlgorithm.processFrame → FaceIDResult
              └─▶ 回调 模块 Activity.handleAlgorithmResult
```

### 8.2 信号流（分心判定）

```
VehicleSignalSource (VHAL 车速) ──▶ VEHICLE_SPEED topic
FrameProcessor 结果 ──────────────▶ ALGO_RESULT topic
                                          │
SignalDispatcher.poll() (SubMaster 轮询)
  车速缓存 + 分心状态机 (防抖 + 车速分档)
      │
      ▼
FRAME_OVERLAY topic ──▶ 绘制层消费 / UI 显示
```

### 8.3 故障上报流

```
某 topic 断流/变慢
  └─▶ BusSubscriber.per-topic 健康检查 → alive=false
        ├─▶ HealthMonitor.update() → onFault 回调（watchdog 上报）
        └─▶ SignalDispatcher.poll() → 发布 SIGNAL_ERROR / FRAME_ERROR
              └─▶ 消费方降级（如车速不可用 → fast 档 1.5s），不崩溃
```

## 9. 容错与故障隔离机制

| 机制 | 实现 | 效果 |
|------|------|------|
| **per-topic 健康检查** | `BusSubscriber.update()` 记录 lastUpdate，超时置 alive=false | 某 topic 断流只影响自身 |
| **reader 独立指针** | `BusQueue` 每个 reader 独立读指针 | 慢读者不阻塞发布者，不被其他读者拖垮 |
| **健康监控 / watchdog** | `HealthMonitor` 检测健康→失活转变并上报 | 上层收到故障通知，可降级 |
| **错误事件分级** | `SIGNAL_ERROR` / `FRAME_ERROR` / `ALGO_STATE` topic | 按故障类型分级响应 |
| **回调异常隔离** | `HealthMonitor.onFault` 回调 try/catch | 故障回调异常不向外传播 |
| **线程隔离** | 每层独立执行器/线程 | 层内异常不跨层传播 |
| **值对象传参** | 载荷均为不可变值对象 | 避免跨层共享可变状态 |

## 16. v3.0 上层应用模块化重构（对应 FACEP-011）

> v3.0 起，上层应用从"单一 `PreviewActivity` 承载所有功能"重构为**主页 + 三大功能模块**，并联动修订算法输入（全图推理）与渲染（按模块分区）。本节为**当前实现**的权威说明。

### 16.1 模块划分与 flag 控制

| 模块 | Activity | 算法 flag | 业务 |
|------|----------|-----------|------|
| 主页 | `ui/HomeActivity`（LAUNCHER） | - | 三入口 + 版本信息 |
| 人脸识别 | `ui/RecognitionActivity` | `DETECTION\|RECOGNITION\|LIVENESS\|LANDMARK` | 检测 + 识别 + 活体 + 68 地标 |
| 疲劳监测 | `ui/FatigueActivity` | `DETECTION\|LANDMARK` | 眼/嘴开合状态 + 68 点位绘制 |
| 分心监测 | `ui/DistractionActivity` | `DETECTION\|HEADPOSE\|GAZE\|LANDMARK` | 头姿 + 视线 + DMS 分区 |

- flag 经 `AlgoSession.acquire(context, flag)` → `FaceIDAlgorithmImpl.setFlagAndReset(flag)`（configure + 重置眼嘴管线），切换模块时正确重建状态，避免疲劳/分心状态残留。
- 旧 `PreviewActivity` 保留为诊断页（已非 LAUNCHER），Makefile `ACTIVITY_NAME=.ui.HomeActivity`。

### 16.2 公共会话：`core/AlgoSession` 与 `core/FrameSession`

均为**进程级单例 + 引用计数**，模块切换复用同一份资源，避免重复创建与数据污染：

```
AlgoSession（算法单例）
  acquire(context, flag)  : refCount++ ；0→1 时 initializeAlgo()（加载模型 + 注入 FaceEnrollmentManager）
                            + setFlagAndReset(flag)
  release()               : refCount-- ；归 0 时 doRelease()（只重置回调，见 §16.4）
  setResultCallback(...)  : 注入模块结果回调

FrameSession（相机/帧单例）
  acquire(frameProcessor, algorithmEnabled) : refCount++ ；0→1 时 attach FrameDistributor
  release()               : refCount-- ；归 0 时 doRelease()（停相机 + detach）
  configureSurface(surface, overlay)       : 配置 GLES2 + renderer + 固定比例居中（§16.3）
  createRenderer()                          : 每模块新建 renderer（避免 GL 上下文冲突）
  frameDistributor()                        : 供模块取 frameW/H 做坐标映射
```

`core/FaceOverlayBridge`：按模块分区组装 `FaceBox` 并设置 overlay `drawMode`；`core/NativeFrameReader`：JNI 帧读取公共化。

### 16.3 预览尺寸：固定比例 + 居中（不依赖帧回调）

- **父容器必须是 FrameLayout**（尊重 `layoutParams.width/height` 与 `gravity`；ConstraintLayout 忽略 width/height）；
- `FrameSession.configureSurface` **不再注册帧尺寸回调**，改为布局完成后基于**固定 1600×1300 常量** + 父容器尺寸算一次（`fitFixedAspect`），并设 `Gravity.CENTER` 居中；
- `resizeTo`：`lp.width/height` **必须无条件设置**（`ViewGroup.LayoutParams` 基类字段）——否则 GLSurfaceView 的 `layoutParams` 非 `FrameLayout.LayoutParams` 时尺寸不生效 → 拉伸；`gravity` 仅对 FrameLayout 设置居中；
- 根因说明：旧实现依赖 `onFrameSizeChanged` 首帧回调，若首帧 `parent.width==0`（布局未完成）会 `return` 且之后尺寸不再变化 → 永不 resize → 拉伸。

### 16.4 生命周期修复：AlgoSession 执行器不可被 shutdown

**问题**：`AlgoSession.doRelease()`（计数归 0 时）原实现 `mAlgoExecutor.shutdown()` + `mAlgorithm.release()`。但两者均为**单例字段不会重建**，再次进入模块时 `FrameProcessor.submitFrame` 调 `mExecutor.submit()` 抛 `RejectedExecutionException` → **算法无响应**（现象：首次进入正常，退出再进入故障）。

**修复**：`doRelease()` 只重置 `mResultCallback`，不销毁算法与执行器，`mInitialized` 保持 true，下次 `acquire()` 直接复用已加载模型：

```kotlin
private fun doRelease() {
    mResultCallback = null
    Log.i(TAG, "doRelease: reset callback, algo kept alive for reuse")
}
```

### 16.5 算法输入：全图推理（取消 ROI 裁剪）

- `FrameProcessor` 取消 900×900 裁剪，改为**全图 1600×1300** UYVY→RGB888 后直接 `processFrame(rgb, 1600, 1300, 0)`；
- `setCropOffset(0, 0)`：算法返回的框/关键点/68 地标**天然为原图坐标，无需点位映射转换**；overlay 直接按原图尺寸缩放显示；
- 移除 `cropFrame`/`updateTracking`；保留 `cropLeft/cropTop=0`（兼容 `FaceOverlayBridge.updateCropRect` / 旧 `PreviewActivity` 编译引用，对应裁剪绘制已不再被模块调用）；
- 性能：有人脸约 82ms（中位数）、无人脸约 35ms，偶发尖峰 160ms+（详见 FACEP-003 §8 变更记录）。

### 16.6 渲染按模块分区（`FaceOverlayView.drawMode`）

| drawMode | 模块 | 绘制内容 |
|----------|------|---------|
| `DRAW_MODE_RECOGNITION` | 人脸识别 | 人脸框（绿 detected / 红 spoof）+ 名称 + 置信度 |
| `DRAW_MODE_FATIGUE` | 疲劳监测 | **68 眼嘴点位** + 眼睛/嘴巴开合状态文字（`E:OPEN/CLOSED M:OPEN/CLOSED`）；**不画**脸框/名称/置信度 |
| `DRAW_MODE_DISTRACTION` | 分心监测 | 头姿信息 + 视线信息 + **关键 5 点**（紫）+ 头姿/视线箭头 + DMS zone 面板 + 分心提示；**不画**脸框/名称/置信度/眼嘴状态 |

### 16.7 人脸识别：已导入数量展示

## 18. 算法数据源澄清与直连底层探索（对应 FACEP-013）

> 本节澄清**算法结果的坐标点位来自哪里**，并记录"绕过 AAR 直连 `libface.so`"这一探索的完整过程与**不可行结论**。当前算法入口仍为 AAR（FACEP-006），未切换。
>
> **v3.3 更新（2026-08-24）**：AAR 算法从 `2d106det_int8.dlc`（106 点）升级为 `pipnet68_int8.dlc`（**PIPNet 68 点 / 300W 标准**），`FaceResult.landmarks` 输出点数由 106 变为 68，其余字段不变。详见 §18.4。

### 18.1 绘制点位的数据来源（当前实现）

所有绘制点位（人脸框 / 5 关键点 / **68 轮廓点** / 头姿 / 视线 / 分区 / 眼嘴状态）均来自 AAR 的 Java `atlas.face.sdk.FaceResult`，经 `FaceIDAlgorithmImpl.processFrame` 转换到 `IFaceIDAlgorithm.FaceIDResult`，再经 `core/FaceOverlayBridge` 组装为 `FaceBox` 供 `FaceOverlayView` 绘制。

Java `FaceResult` 实际字段（`javap` 反编译确认；v3.3 起 `landmarks` 为 68 点）：

```
float[]    box;          // 人脸框
float      score;        // 置信度
float[][]  keypoints;    // [5][2] 5 关键点
float      liveness;     // 活体
float[][]  landmarks;    // [68][2] 68 轮廓点（PIPNet/300W 标准，v3.3 起）
float[]    embedding;    // [512]
int        flags;
float      headPitch, headYaw, headRoll;           // 头姿
float      gazeYaw, gazePitch, gazeDistracted;     // 视线
int        gazeValid; int gazeCalibrated;
int        zoneId; float zoneConfidence;           // DMS 分区
float      distractionScore, distractionHpScore, distractionGazeScore;
```

> **重要澄清**：新版 AAR 的 `FaceResult` **包含头姿/视线/分区字段**，`FaceIDAlgorithmImpl` 中 `r.headPitch/r.headYaw/r.headRoll`、`r.gaze*`、`r.zoneId` 均可正常取值。早期"新 AAR 移除了头姿字段"的误判已被修正（详见 FACEP-013 §2.4）。

### 18.2 直连 `libface.so` 的探索与结论

为验证轮廓点/点位是否来自底层真实数据（v3.2 探索时 AAR 为 106 点），尝试绕过 AAR 的 Java/JNI 包装层，通过自研 JNI 直接调用 AAR 内 `libface.so` 导出的 `face_vision_*` C API（返回 `CFaceResult` C 结构体）。共尝试 6 种加载方案：

| # | 方案 | 结果 |
|---|------|------|
| 1 | `dlopen("libface.so")` + `dlsym` | ❌ 报错：`libSNPE.so is not accessible for the namespace "classloader-namespace"` |
| 2 | 先 `dlopen("/system/lib64/libSNPE.so")` 再 `dlopen("libface.so")` | ❌ 全路径加载 `libSNPE.so` 也被命名空间拒绝 |
| 3 | `RTLD_LAZY` / `RTLD_NOW` / `RTLD_NOLOAD` 变体 | ❌ 依赖 `libSNPE.so` 的 NEEDED 解析仍触命名空间隔离 |
| 4 | `android_dlopen_ext` + `ANDROID_DLEXT_USE_NAMESPACE` | ❌ `library_namespace` 实为私有指针，无法从非公开 API 获取合法句柄 |
| 5 | 编译期链接 `libface.so`（IMPORTED + NEEDED） | ❌ `SONAME=libfacevision.so` 需重命名匹配；加载仍卡 `libSNPE.so`；即便成功 `face_vision_init` 调用崩溃 |
| 6 | 将 `/system/lib64/libSNPE.so` 打包进 APK | ⚠️ `libface.so` 能 `dlopen` 成功、`version=1.0.0`；**但 `face_vision_init` 调用崩溃**（SNPE 运行时/参数不匹配） |

**结论（不可行）**：
1. 底层 `libface.so` 强依赖高通 `libSNPE.so`，受 Android linker **命名空间隔离**，普通 app 无法在自身命名空间直接加载；
2. C 层 `CFaceResult` **不含**头姿/视线/分区字段——自研 JNI 直连只能拿到检测/关键点/地标，反而丢失更高层业务数据；
3. 即便打包 `libSNPE.so` 使 `dlopen` 成功，`face_vision_init` 仍崩溃，无稳定运行方案。

**处置**：所有自研 JNI 实验代码（`native_face_sdk.cpp`、`NativeFaceSDK.kt`）**已回退删除**，维持 AAR 方案为唯一算法入口。

### 18.3 后续建议

- 如需排查轮廓点/点位正确性，应使用 AAR 自带的 `FaceSDK.setDebugDumpPath` 导出原始 landmarks 比对，而非绕过 AAR；
- 若需更高性能，应推动算法团队在 AAR 层优化，而非直连底层 SO；
- AAR 的 `libface.so` / `libface_vision_jni.so` / `libSNPE.so` 是一体交付物，不应拆开单独使用。

### 18.5 眼睛开合度距离解耦与闭眼阈值收紧（v3.4，2026-08-24）

> 实测问题：**近距离判睁眼、远距离判闭眼**——同一睁眼状态，人脸离摄像头近时判定正常，拉远后 EAR 系统性偏低被误判闭眼。本轮对眼睛开合度归一化重构并收紧闭眼阈值，对应 `EyeMouthStateEstimator` / `EyeMouthStateMachine` / `EyeMouthCalibrator` 三处。

#### A. 根因：经典 EAR 的分母太小

经典 EAR = 上下睑纵向距离均值 / **单眼眼角距**。理论上尺度不变，但分母（单眼角距）很短，远处人脸变小时地标**绝对误差占比**显著放大，EAR 系统性偏低 → 误判闭眼。

#### B. 方案：开合度改为脸宽归一化（aperture）

`EyeMouthStateEstimator` 开合度分母由单眼角距改为**双眼外眼角距离（脸宽代理）**：

```
aperture = avg( |上睑[i].y − 下睑[i].y| )  /  (|右外眼角.x − 左外眼角.x|)
```

- 远处脸小时，分子（睑距）与分母（脸宽）**同比例缩小**，比值与距离解耦；
- 分母远大于单眼角距，远处小脸时对地标噪声更鲁棒；
- **归一化基准**（构造参数，可校准）：`referenceEyeAperture=0.10`（完全睁眼）、`closedEyeAperture=0.02`（闭眼残差），`eyeOpenRatio=(aperture−0.02)/(0.10−0.02)` 截断到 0~1；
- `EyeMouthEstimate` 保留 `ear`（原始 EAR）与 `faceWidth`（脸宽像素）为**诊断字段**（`[EYE-CAL]` 采集日志输出）；外眼角缺失（自定义映射未配外眼角）时自动**回退经典 EAR**；
- 嘴巴 MAR 不变（仍为嘴角距分母）。

#### C. 闭眼判定阈值收紧（当前生效）

| 参数 | 值 | 位置 | 说明 |
|------|-----|------|------|
| `eyeCloseRatio` | **0.10** | `EyeMouthStateMachine` 构造默认 | 开合度 ≤ 0.10 才进入闭眼候选（未校准时兜底） |
| `DEFAULT_CLOSE_RATIO_FACTOR` | **0.10** | `EyeMouthCalibrator` | 动态闭眼阈值 = 闭眼基准 + (睁眼基准−闭眼基准)×0.10（aperture 量纲，见 §18.7） |
| `CalibratedThresholds.DEFAULT.eyeCloseRatio` | **0.10** | `EyeMouthCalibrator` | 未校准（样本不足）时的默认闭眼阈值，与状态机同步 |

- **演进**：静态/默认阈值 `0.18 → 0.12 → 0.10 → 0.08 → 0.10`（0.08 时实车反馈闭眼过难触发，回退放宽），动态下界因子 `0.35 → 0.20 → 0.15 → 0.10`，配合"退出闭眼即时解除"的不对称防抖（见 §18.6），在防误报与可触发之间折中；
- **未动**：睁眼侧上界因子（0.70）、确认时长（眼睛/嘴巴均 80ms，嘴巴张嘴 200ms）、嘴巴全部阈值；睁眼候选默认阈值由 0.35 放宽至 **0.30**（配合退出即时解除，详见 §18.6）；
- **v3.5 修订**：动态校准改为**跟踪未归一化 aperture/MAR**，阈值在原始量纲计算后按个人实测基准换算成 ratio 喂状态机（`EyeMouthCalibrator.update(eyeEst.aperture, eyeEst.mar)` + `normalizeEye/normalizeMouth`）；**眼睛阈值恒为因子位置（0.10/0.70），校准激活无跳变**；**嘴巴阈值固定 0.60/0.35**（不随动态校准漂移）；静态阈值与静态归一化基准仅作**未接入动态时的兜底 / 初始端点**，详见 §18.7；
- 设备端可用 `[EYE-CAL]` 日志的 `aperture` 实测标定归一化基准（睁眼典型值 / 闭眼残差）；v3.5 起该基准仅作为个人基准的**初始端点**，运行中由分位数跟踪自动贴合每个人。

### 18.6 退出闭眼不对称防抖（v3.4，2026-08-24）

> 实车反馈：进入闭眼规则收紧后，出现"**睁大眼睛仍被判闭眼**"——退出方向的判定条件反而比进入方向苛刻，状态恢复迟钝。本轮将退出方向改为**即时解除**，对应 `EyeMouthStateMachine` / `FatigueActivity` 两处。

#### A. 问题：退出方向的两层苛刻条件

1. **`EyeMouthStateMachine.AxisState`**：从闭眼切回睁眼要求 `eyeOpenRatio ≥ 上界`（默认 0.30，动态 `低位 + 区间×0.70`）**连续 80ms**；真实值贴着上界轻微抖动（光照/姿态/归一化偏差）时计时反复重置，永远凑不满；
2. **`FatigueActivity`**：退出闭眼告警与进入对称，需**连续睁眼 3000ms**（`EYE_CLOSE_ALERT_MS`），期间眨眼或单帧抖动即清零重来。

#### B. 方案：不对称防抖（进入严格、退出即时）

- **`EyeMouthStateMachine`**：`AxisState` 已确认"关闭"（闭眼/张嘴）后，打开候选（睁眼/闭嘴）**满足即立即解除**，不再累计确认时长；进入方向保持严格确认（眼睛 80ms / 嘴巴 200ms）不变；
- **`FatigueActivity`**：退出告警阈值与进入解耦，新增 `EYE_CLOSE_CLEAR_MS=500` / `YAWN_CLEAR_MS=500`（进入阈值 3000 / 2000ms 不变）；
- **防误报不受影响**：退出需 `ratio` 明显越过上界（0.30 或动态上界），闭眼残差不会误触；即使单帧误触，进入方向仍要 80ms / 3s 确认，不会因此误报闭眼。

### 18.7 校准器跟踪原始量纲 + 个人基准归一化（v3.5，2026-08-24）

> 实车排查（结合 §18.6"睁大眼睛仍判闭眼"反馈）：校准器此前在**已归一化且截断的 0~1 开合度**上做分位数跟踪，动态阈值 `低位 + 区间×0.70` 在混合驾驶（80% 睁眼 ratio≈0.9 / 20% 闭眼 ≈0.05）下被顶到 **≈0.65**；而静态归一化基准（0.10/0.02）与实测不匹配时，完全睁眼只映射到 0.5~0.6（饱和），永远够不着 0.65 → 仍判闭眼。本轮将校准器改为跟踪**原始量纲**并**个人化归一化**，对应 `EyeMouthCalibrator` / `FaceIDAlgorithmImpl` 两处。

#### A. 改动内容

1. **校准器跟踪未归一化 aperture / MAR（真实几何量）**：`EyeMouthCalibrator.update(eyeAperture, mouthMar)` 参数由 0~1 ratio 改为原始量纲（眼睛 aperture=睑距/脸宽、嘴巴 MAR），分位数跟踪（高/低基准）与阈值计算全部在原始量纲下进行；
2. **个人基准归一化**：新增 `normalizeEye(aperture)` / `normalizeMouth(mar)`，用该驾驶员**实测高/低基准**（EWMA 平滑）做归一化端点，完全睁眼恒映射 ≈1.0、完全闭眼 ≈0.0。彻底取代静态 0.10/0.02 端点错配导致的饱和失真；静态端点仅作**基准未建立时的初始值/兜底**；
3. **阈值换算（恒因子，校准激活无跳变）**：原始量纲下滞回阈值 `低位 + 区间×factor`，经同一基准归一化后等价于**因子位置本身**（眼睛上界 0.70 / 下界 0.10），`CalibratedThresholds` **恒输出眼睛因子**——无论样本是否充足（未校准阶段输入走静态端点归一化，校准激活仅平滑切换归一化端点、阈值不跳变；修复旧实现"样本不足 0.30 → 基准建立瞬间 0.70"的状态机阈值突变）；**嘴巴阈值固定**（张嘴 0.60 / 闭嘴 0.35，状态机设计为不随动态校准漂移，与构造默认一致，`mouth*` 字段取用后行为不变）；
4. **单态保护**：窗口内高/低位未分离（持续闭眼/闭嘴或持续睁眼/张嘴）时，不再让双基准同时收敛（否则区间塌缩、残差被"正常化"映射到高位，持续闭眼反而判睁眼），改为只让主导侧基准跟随（低位单态→低位跟随残差、保留睁开记忆；高位单态→高位跟随开度、保留残差记忆）；
5. **顺手修复 `AxisRef.reset()` 硬编码**：此前写死眼睛默认值，门开关复位后嘴巴基准错位（应为 0.35/0.62）；现各轴恢复自身初始端点。

#### B. 调用链（`FaceIDAlgorithmImpl.processFrame`）

```
eyeEst = EyeMouthStateEstimator.estimate(landmarks)   // aperture / mar（原始量纲）
validEst = eyeEst?.takeIf { it.valid }                 // 眼睑区域齐全且几何可算才校准
if (validEst != null) {
    if (validEst.faceWidth > 0f) EyeMouthCalibrator.updateEye(validEst.aperture)  // 主路径 aperture
    if (validEst.mar > 0f) EyeMouthCalibrator.updateMouth(validEst.mar)           // 嘴巴数据真实
}
calibrated = EyeMouthCalibrator.thresholds()           // 分位数跟踪 + 阈值换算
eyeOpenRatio = validEst?.let { EyeMouthCalibrator.normalizeEye(it.aperture) } ?: 1f
mouthOpenRatio = validEst?.let { EyeMouthCalibrator.normalizeMouth(it.mar) } ?: 0f
EyeMouthStateMachine.update(true, eyeOpenRatio, mouthOpenRatio, calibrated)
```

**数据真实性防线（v3.5 高危修复，2026-08-24）**：校准器**只收量纲正确、数据真实的帧**，缺失/异常帧不更新基准：
- `eyeEst == null || !valid`（地标/眼睑区域缺失）→ 跳过校准（避免 0 值污染分位数），直接喂当前阈值；
- `faceWidth == 0`（外眼角缺失，`aperture` 回退为经典 EAR，量纲 ≈0.2~0.5 ≠ aperture 0.02~0.12）→ **不喂眼睛轴**，否则高位基准被 EAR 帧抬升、完全睁眼被归一化压低而误判闭眼；
- `mar == 0`（嘴巴区域缺失，估计器置 0 为缺失哨兵）→ **不喂嘴巴轴**，否则低位基准被拉向 0、闭嘴残差被"正常化"到中位，闭嘴候选永不成立、张嘴状态无法解除；
- 校准器内部再兜底：`NaN` 与 `≤0` 样本一律忽略（正常量纲恒 >0：aperture 闭眼残差 ≈0.02+、MAR 闭嘴残差 ≈0.35+）。
- 归一化输出不受上述防线影响：缺失帧回退 `1f/0f`（睁眼/闭嘴），与估计器 `INVALID` 语义一致。

#### C. 行为变化

- **睁眼候选语义**：动态睁眼阈值从"归一化 ratio ≈0.65（受静态基准错配影响、可能够不着）"变为"个人睁闭区间的 70% 位置"——完全睁眼恒可达，半睁（区间中部）落入滞回区间维持上一状态，"睁大眼睛仍判闭眼"消除；
- **持续闭眼不再放松阈值**：旧实现长时间闭眼会稀释"闭眼"语义、睁眼阈值下移误判睁眼；单态保护下闭眼残差恒映射低位，疲劳告警在持续闭眼下仍可触发；
- **校准激活无阈值跳变**：眼睛阈值恒为因子位置（0.10/0.70），未校准阶段与基准建立后一致，状态机不会因"0.30→0.70"突变抖动；`CalibratedThresholds.DEFAULT` 与状态机构造默认完全一致（0.10/0.30/0.35/0.60），修正了此前嘴巴 0.18/0.35 的错位；
- **嘴巴阈值固定**：张嘴 0.60 / 闭嘴 0.35 不随动态校准漂移（状态机设计决策，防止说话等快速开合造成判定漂移）；嘴巴校准仅个人化 `normalizeMouth` 端点，`CalibratedThresholds.mouth*` 恒输出固定值，字段被状态机取用后行为与固定阈值完全一致；
- 归一化输入与阈值端点**一致**（同一 low/high），阈值与输入始终同量纲，无换算错位。
