# 提案：动态 ROI 裁剪 — 算法输入仅传人脸采样区域

> 提案编号：FACEP-003  
> 创建日期：2026-07-01  
> 状态：已实现

---

## 1. 动机

当前算法处理全图 1600×1300（~4MB），DSP 推理 ~70ms。实际有用的只有人脸周围区域，大量像素浪费在无关背景上。通过 ROI 裁剪可以：

- 减小算法输入数据量（4MB → 约 0.8MB），降低 memcpy 和 DSP 带宽
- 为未来提高算法帧率留出空间

## 2. 裁剪窗口规格

### 2.1 尺寸

**固定正方形**。

```
winSize = 900px
```

裁剪窗口恒为 **900×900**，在原图坐标系下。

### 2.2 位置——跟随人脸

裁剪窗口跟随人脸位置，目标是让人脸处于窗口的黄金分割点（0.382）：

```
┌─────────────────────┐
│     H*0.382         │
│      ┌─────────┐    │
│      │  ● 人脸  │    │  ← 人脸中心在黄金分割点
│      │  (虚线)  │    │
│      │  H*0.618  │    │
│      │          │    │
│      └─────────┘    │
│                     │
└─────────────────────┘
```

**跟踪规则：**

```
winCenterY = faceCenterY + winSize * 0.118
winCenterX = faceCenterX
```

即人脸中心在窗口纵向 0.382 处（黄金分割点）。

**边缘约束：**

当窗口触及图像边界时，钳位到边缘，不再移动：

```
winLeft = clamp(winCenterX - winSize/2, 0, imgW - winSize)
winTop  = clamp(winCenterY - winSize/2, 0, imgH - winSize)
```

此时人脸位置继续变化，但窗口位置固定，人脸在窗口内移动。

### 2.3 无人脸时的行为

- 首帧或人脸丢失：窗口居中
- 后续检测到人脸：按跟踪规则移动
- 连续丢失人脸超过阈值（如 30 帧）：回到居中

## 3. 数据流

```
修改前：
  全图 byte[] (1600×1300, 4MB) → processFrame → DSP ~70ms

修改后：
  全图 byte[] (1600×1300)
    │
    ├── EvsGL20CameraRenderer 渲染全图（不变）
    │
    └── 裁剪 ROI (900×900, ~1.6MB) → processFrame → DSP 减少
```

裁剪在算法线程的 `processFrame` 之前完成，从已读取的 `byte[]` 中截取 ROI 区域。

## 4. UI 绘制

在 `FaceOverlayView` 上绘制黄色虚线矩形框表示当前裁剪区域：

- 颜色：黄色（`Color.YELLOW`）
- 样式：虚线描边（`DashPathEffect([10, 8], 0)`），线宽 2px
- 位置：跟随裁剪窗口坐标（与原图坐标一致，`setFaces` 时随 imgW/imgH 缩放）
- 无需标签文字

## 5. 修改范围

| 文件 | 修改 | 说明 |
|---|---|---|
| `FaceIDAlgorithmImpl.kt` | `processFrame` 入口处裁剪 byte[] 后再调用 nativeDetect | 核心改动 |
| `FrameProcessor.kt` | 传递人脸框信息到裁剪逻辑 | 接口调整 |
| `FaceOverlayView.kt` | 新增黄色画框画笔 + 绘制裁剪区域矩形 | UI |
| `PreviewActivity.kt` | 传递裁剪窗口坐标到 overlay | ~3 行 |

## 6. 效果预期

- **算法输入**：全图 4MB（1600×1300 UYVY）→ 裁剪 1.6MB（900×900 UYVY），减少 ~60%
- **DSP 推理耗时**：~70ms → ~20-30ms（预估，取决于模型输入尺寸适配）
- **全图显示**：不变，用户看到的是完整画面
- **裁剪窗口**：实时跟随人脸，边缘自适应钳位

## 7. 风险

- 模型输入尺寸：确认 DSP 模型是否接受可变输入尺寸。若不可变，则需要补边（padding）到模型要求的固定尺寸
- 人脸快速移动时窗口可能有延迟：需评估跟踪平滑度，必要时加插值
- 人脸贴近边缘时裁剪区域可能只包含半张脸，影响识别精度

## 8. 变更记录（2026-08-21）：取消图像裁切，改用全图推理

> **结论：本提案的 ROI 裁剪方案已回退，算法改为直接使用全图 1600×1300 做推演。**

### 8.1 变更动机

- **省去点位映射转换**：裁剪方案需要在算法内用 `setCropOffset(cropLeft, cropTop)` 把裁剪空间坐标修正回原图空间，坐标换算易错、易引入偏差；
- **对齐模块化（FACEP-011）**：取消裁切后，算法返回的框/关键点/106 地标**天然为原图坐标**，`FaceOverlayBridge` 直接按原图尺寸（1600×1300）缩放显示，三个模块共用同一套坐标语义，无映射逻辑。

### 8.2 变更内容

| 项 | 原设计（FACEP-003） | 实际落地（全图推理） |
|----|--------------------|---------------------|
| 算法输入 | 900×900 ROI 裁剪（UYVY→RGB888 一次转换） | 全图 1600×1300（UYVY→RGB888 一次转换） |
| 裁剪窗口 | `winSize=900`，跟随人脸（黄金分割 0.382） | **取消**（无裁剪、无窗口跟踪） |
| 坐标修正 | `mAlgorithm.setCropOffset(cropLeft, cropTop)` 修正回原图 | `setCropOffset(0, 0)`，坐标即原图坐标 |
| 跟踪 | `updateTracking` 移动裁剪窗口 | 删除（不再需要） |
| 黄色采样框 | `FaceOverlayView.setCropRect` 绘制裁剪区域 | `FaceOverlayBridge.updateCropRect` 不再被模块调用（保留字段 `cropLeft/cropTop=0` 兼容编译） |

**涉及文件**：`algorithm/FrameProcessor.kt`（核心，`convertFullFrame` 全图转换替代 `cropFrame`）。

### 8.3 性能影响

| 场景 | 900×900 裁剪 | 1600×1300 全图 |
|------|-------------|---------------|
| 有人脸每帧 | ~70ms | ~82ms（中位数），偶发尖峰 160ms+ |
| 无人脸每帧 | ~30ms | ~35ms |

全图推理计算量更大（输入 1600×1300 ≈ 208 万像素 vs 900×900 ≈ 81 万像素），但**省去坐标映射**，代码更简单、点位对齐更稳。若后续需提速，可评估：恢复裁剪+映射，或算法侧优化全图输入。

### 8.4 保留字段说明

`FrameProcessor.cropLeft` / `cropTop` 保留（全图推理下恒为 0），因 `FaceOverlayBridge.updateCropRect` / 旧 `PreviewActivity` 仍引用这些字段（编译依赖）；对应裁剪绘制方法已不再被三模块调用。
